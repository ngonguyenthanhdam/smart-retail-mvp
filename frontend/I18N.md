# VI/EN and numeric display

The frontend defaults to Vietnamese. The VI/EN control changes React context in place, preserving form inputs, filters, modal state, cart values, authentication and the current URL. The `retailsense-locale` cookie stores the preference. Server Components read the same cookie for the initial HTML language and metadata, preventing a different server/client initial locale. No locale routing, reload or authentication change is required.

## Translation architecture

- `src/i18n/messages/`: typed, paired VI/EN namespaces for common UI, administration, authentication, operations, reports, inventory and planning.
- `src/i18n/screens/`: screen-specific copy, including AI data, training, results and chat controls.
- `src/i18n/dynamic.ts`: paired interpolation functions. Arguments retain their original values.
- `src/i18n/provider.tsx`: `useLocale`, `useMessages` and `useScreen`; `server.ts` supplies request-specific server copy.
- `src/i18n/fallback.ts`: missing/empty English entries fall back to Vietnamese. Compile-time dictionary shapes and unit tests catch key/signature mismatches before release.
- `src/i18n/feedback.tsx`: re-renders frontend feedback that was already stored before the locale changed. Only known application copy/templates are mapped; product names, notes and imported cells must not use this helper.

This extends the existing TypeScript dictionaries and React context without a runtime i18n dependency. Both small locale catalogs are bundled for synchronous switching. Larger catalogs can later be split by route if bundle measurements justify it.

Coverage includes login, password recovery/reset, navigation, dashboard/reports, stores/warehouses, users/roles, products, categories, units, store product settings, inventory/lots, purchases/receiving, sales/cart/invoice details, expenses, imports, forecasts, replenishment, alerts, AI Center and not-found content. There is no separate registration, roles or general settings screen in this checkout; roles are managed under Users and product settings under Products.

Names, addresses, notes, user-defined unit labels, CSV cells, model identifiers, AI answer text and free-form backend messages remain as supplied. Backend errors are localized only from explicit error codes/status fallbacks. Unknown messages are preserved because the frontend cannot safely infer their meaning. Known AI business-source table columns are mapped by tool identifier and explicit schema; arbitrary uploaded columns remain unchanged.

## Money and units

`src/lib/format.ts` centralizes `formatVND`, `formatQuantity`, `formatUnit` and `formatQuantityWithUnit`. VND uses dot thousands and comma decimals in both locales, e.g. `10000.50` → `10.000,5 VND`. API Decimal strings are formatted without conversion to `Number`; meaningful precision is preserved. Invalid/missing values display `—`, never an invented zero. The formatter does not feed business calculations.

`G`/`GRAM` and `KG`/`KILOGRAM` display as `g` and `kg`; `ML` and `L` are normalized consistently. Other symbols/names come from metadata and remain unchanged. There is no conversion of quantities or unit ratios. Missing unit metadata is labeled explicitly in the selected language. Aggregate dashboard quantities across products are identified as totals across different units, since the API does not provide one valid common unit.

VND formatting covers product prices, store settings, dashboard KPIs/charts, inventory costs, purchases, sales, discounts, invoice details, expenses, forecasts, replenishment estimates and structured AI sources. Quantity labels cover product units, inventory/lots, forms, sale lines, purchase lines, forecasts and AI charts. Existing arithmetic, conversion ratios, request payload values and backend/database code are unchanged.

## Verification

Run from `frontend` with the repository's Node 22 version:

```text
npm ci
npm run typecheck
npm run lint
npm test
npm run build
npm run test:browser
```

`@playwright/test` is the only added development dependency. Browser tests use installed Chrome by default. Set `PLAYWRIGHT_CHANNEL=chromium` after installing Playwright Chromium to use that browser instead. Set `PLAYWRIGHT_PRODUCTION=1` after building to run the same suite with `next start`. Stop any existing server before a production verification, because the config allows reusing a server on port 3000.

Unit tests cover exact money formatting, invalid and boundary inputs, g/kg/custom/missing units, locale defaults, fallback behavior, every bilingual namespace, interpolation signatures, error mapping and preserved user text. An AST audit detects Vietnamese literals in components/routes, allowing only language names and documented API column keys.

Browser tests cover all 16 main routes in both languages, login/logout and cookie persistence, validation, role guards, unchanged URLs, filters, product forms, sale payloads, purchase/expense payloads, inventory lots, forecast quantities, AI charts, modal switching and keyboard control at 390/768/1440 pixels. Every scenario checks runtime/React/hydration errors. Test screenshots and failure traces are kept in the ignored `.test-artifacts/i18n` directory.

The browser suite intercepts API calls with synthetic fixtures and blocks external requests. It validates frontend behavior and outgoing payloads without writing to a live database. It does not establish live backend/database integration, production data correctness or AI model accuracy. Free-form server errors, uploaded data and AI answers may use their original language by design.

Verification on 2026-11-09: typecheck, zero-warning lint, the default Turbopack production build, 9 unit tests and 31 Chrome scenarios against `next start` passed. Screenshots were reviewed for desktop, mobile, dashboard, product dialog and AI results. Production testing caught and fixed the fallback section route's static-rendering conflict with the locale cookie. A stale build-cache/process failure was resolved by removing the generated `.next` directory and rebuilding; the bundler configuration is unchanged.
